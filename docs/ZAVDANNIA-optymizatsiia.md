## Перш ніж почати
1. Прочитай ZAVDANNIA.md повністю: порядок роботи, «Правила коду», «Що вже є», «Не робити», журнал злиттів.

## Архітектура коротко
- **Збирання:** `src/js/*.js` (≈152 модулі, порядок — у `src/manifest.json`) + `src/styles.css` + вбудовані шрифти (`src/fonts`) → `node build.mjs` → `build/app.html`, `pervynnyi-ohliad.html`, `index.html`, `sw.js`.
- **Обгортки.** Нове додається новими модулями, які обгортають наявні функції: `{ const x0 = fn; fn = function(){ const r = x0.apply(this, arguments); …; return r; }; }`. Через це `update()`, `show()`, `renderPaper()`, `applyView()`, `uiStyleApply()`, `popRender()`, `layoutTabs()` мають довгі ланцюжки обгорток.
- **Стиль «Apple»** — модулі 664–672. Він працює через класи на `<html>`: `ui-ios`, `ui-start`, `ui-nonexam`, `pt-side`, `ust-empty`. «Класичний» стиль має лишатися таким, як був.
- **Друк** іде через `#print` і лише чорним і білим (старі лазерні принтери). На це є тест.
- **Порожні бланки** — масив `FBLANKS` (модулі 658, 668–670), друк через `printBlanks()`.

## Етап 1 — аудит
Спершу лише звіт, без змін коду: PR із файлом `docs/AUDIT-2026-11.md`.

### a) Швидкодія
- Заміряй:
  - час від відкриття до готовності;
  - час від натискання варіанта до оновлення тексту (`update()` з усіма обгортками);
  - перемикання розділу (`show`), «Перед друком» (`renderPaper`), окреме вікно ⧉.
- Міряй через Playwright + `performance.now()` на двох пацієнтах:
  - порожньому;
  - заповненому: шаблон «Негоспітальна пневмонія», 10 щоденників, 15 призначень, 20 записів журналу обстежень.
- Ціль: реакція на натискання ≤ 50 мс, відкриття ≤ 1,5 с при CPU throttling ×4.
- Назви найдорожчі обгортки з цифрами. Відомі кандидати: `uilApply()` і `stApply()` викликаються в кожному `update()` і щоразу проходять усі `SECTIONS`. Їх можна кешувати або викликати лише при зміні.

### b) Розмір
`build/app.html` важить ≈ 2,9 МБ.
- Покажи, скільки з цього припадає на шрифти, CSS, JS і дані.
- Знайди мертвий CSS: правила, які повністю перекриті пізнішими, і правила для елементів, яких немає. Знайди дублікати.
- Оціни, чи можна залишити у шрифтах лише кирилицю й латиницю. Не можна втратити гліфи, потрібні в бланках: ° ² ₂ → × ± № ’ « » – —.

### c) Надійність
- Помилки й попередження в консолі на всіх документах: огляд, щоденник, призначення, епікриз, 066/о, 028/о, анестезіолог, консиліум, довідка, згода.
- Витоки: MutationObserver, слухачі scroll/resize, setInterval.
- Подвійні обробники після 5 перемикань «Apple» ↔ «Класичний».
- Поведінка без localStorage (приватне вікно) і з дуже великою базою пацієнтів: 500 вигаданих пацієнтів.

### d) Доступність
- Прожени axe-core на основних екранах: npm у devDependencies, лише для тестів.
- Контраст у стилі «Apple», денна й нічна теми.
- Фокус із клавіатури: Tab по формі, бічне меню в режимі «лише значки», межа ширини меню (стрілки), меню «Профіль», «Вигляд», діалог «Бланки».
- Підписи кнопок-значків: ⧉, ⤢, ⇥, ↶, «»», лупа пошуку.

### e) Зручність
- Пройди шлях лікаря й порахуй кліки:
  - до готового первинного огляду;
  - до друку щоденника;
  - до виписного епікризу.
- Назви, що дублюється, заважає або незрозуміле.
- Запропонуй 5–10 конкретних покращень із вигодою «до / після» в кліках або секундах.
- Не пропонуй змінювати медичні тексти, шаблони хвороб чи схеми лікування.

**Формат кожного пункту звіту:** що знайдено → доказ (цифри, скриншот або рядок коду з шляхом) → пропозиція → ризик → оцінка обсягу (S/M/L). Наприкінці звіту — пріоритетний список PR для етапу 2.

## Етап 2 — виправлення
Починай лише після того, як лікар погодить звіт. Невеликими окремими PR, один PR — одна тема. Порядок за звітом, орієнтовно:
1. **Швидкодія:** кешування, виклик лише при змінах, debounce/requestAnimationFrame, менше перебудов DOM. Поведінка не змінюється.
2. **Надійність:** помилки консолі, витоки, подвійні обробники.
3. **Розмір:** мертвий CSS і дублікати; шрифти — лише якщо погоджено.
4. **Доступність** — за списком зі звіту.
5. **Погоджені покращення зручності** — лише в стилі «Apple».

Кожен PR має містити:
- тест у `tests/features.cjs` (перед рядком «Без помилок JavaScript»), який ловить проблему або фіксує поліпшення. Для швидкодії — заміри в окремому скрипті `tests/perf.cjs`, без порогів, що падають через повільний CI;

- нову версію (`VERSION`, `VDATE`) і рядок CHANGELOG українською в `src/js/120-version-changelog.js`;
- оновлений `pervynnyi-ohliad-prev.html`: `git show origin/main:pervynnyi-ohliad.html > pervynnyi-ohliad-prev.html`;
- зелений CI на GitHub (11 перевірок);
- рядок у «Журнал злиттів» ZAVDANNIA.md після злиття.

## Обмеження
- **Не зливай жоден PR без явного «зливай» від лікаря.** Готовий PR із зеленим CI — це кінець твоєї роботи над ним.
- **Не змінюй** формат збереження пацієнтів, «Справу пацієнта», резервні копії, папку даних, імпорт/експорт.
- **Не чіпай медичний зміст:** шаблони хвороб, дози, схеми антибіотиків, перевірки СОП закладу (модулі 659–661), тексти бланків МОЗ (003/о, 027/о, 028/о, 066/о, 003-3/о) і Додатків СОП. Виняток — коли зламано відображення.
- **Жодних даних пацієнтів** у коді, тестах і скриншотах — лише вигадані: «Тестовий Пацієнт», «Історія 7».
- **Друк** — лише `#000` і `#fff`, без сірого.
- **Офлайн.** Програма має працювати з файлу, без мережі. Нових зовнішніх залежностей у зібраному файлі не додавай; для тестів — можна.
- **Правила коду** з ZAVDANNIA.md:
  - нове — окремим модулем у кінці `manifest.json`;
  - стилі — у кінець `styles.css` з коментарем версії;
  - наявне обгортай, а не переписуй.
  Виняток — оптимізація, погоджена у звіті: тоді можна змінити наявну функцію, якщо тести доводять, що поведінка та сама.
- **Великі зміни.** Якщо зміна зачіпає понад 3 наявні файли — спершу опиши план у PR і чекай відповіді.
- **«Класичний» стиль** має виглядати й працювати як раніше.
